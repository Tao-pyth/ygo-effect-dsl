# ADR 0021: v1.0.0 build provenance and reproducibility

## Status

Accepted for v1.0.0 production distribution qualification.

## Context

v1.0.0 publishes release artifacts only when the artifact can be traced back to a source commit, build command, fixed environment, and SHA-256 checksum. The release set is wheel, sdist, Windows executable, and Windows portable package. Installer metadata stays in the release artifact composition evidence, even when the current distribution package is the portable zip.

## Decision

Every CI release build sets `SOURCE_DATE_EPOCH` from the current Git commit timestamp and records the source commit, source tree, package version, Python version, builder OS, machine, `GITHUB_SHA`, `GITHUB_RUN_ID`, artifact path, artifact size, and SHA-256. The build provenance manifest and checksum file are generated by `python -m ygo_effect_dsl.spikes.build_provenance_manifest`.

The fixed build environment is:

- Ubuntu wheel and sdist: `ubuntu-latest`, Python 3.10, `python -m build`, dependency lock from `pyproject.toml`, build command recorded in workflow logs, and `SOURCE_DATE_EPOCH` from the source commit.
- Windows executable and portable package: `windows-latest`, Python 3.10, PyInstaller, dependency lock from `pyproject.toml`, compiler/toolchain from the hosted image, build command recorded in workflow logs, and `SOURCE_DATE_EPOCH` from the source commit.

The Ubuntu workflow builds wheel/sdist twice from two independent Python virtual environments, `.build-env-primary` and `.build-env-independent`, into `dist-primary` and `dist-independent`. It writes `release-checksums.json` and `reproducible-build-comparison.json`. Hash differences do not become invisible: each differing artifact must be explained as field-level differences before publication. The comparison file is the release-time attestation input for whether the build is reproducible or has accepted non-reproducible fields.

The Windows workflow writes `windows-checksums.json` and `build-provenance-windows.json` for the CLI executable, desktop Windows executable, and portable zip. Authenticode signing is a separate gate; unsigned CI artifacts are not release eligible. Independent Windows rebuild comparison and attestation must be completed before the final GitHub Release if any field-level differences remain.

No third-party core, card database, CardScripts, card images, or card text are bundled into wheel, sdist, Windows executable, installer, or CI artifacts without explicit distribution approval.

## Consequences

The production gate can reject missing build provenance before release publication. The release manager can trace every artifact back to the source commit and compare the published SHA-256 values against the build provenance manifest.
